# 自主表型采集与育种分析 Agent：三轨开发路线

> 状态：方向草案，作为后续设计讨论与任务拆分的基线，不直接授权数据模型或公开接口变更。
>
> 目标读者：Pod Agent 开发者、测试者与未来参与试用的育种人员。
>
> 当前开发分支：`feat/phenotype-breeding-agent-demo`。

## 结论

初代 Demo 不应从零重做 Agent，也不应先引入 FastAPI 或照搬重型框架。仓库已经具备“相机 → YOLO → 表型聚合 → SQLite → 工具调用 → LLM 总结 → CSV 导出”的主干，下一阶段最有价值的工作是把它变成一个**数据可复核、分析有证据、行动有边界**的完整育种任务闭环。

三条路线并行但不等权：

1. **目标线**定义产品到底替育种人员完成什么，以及什么结果才算成功。
2. **理论线**只学习马上要用的 Rust、Tauri、Agent 与育种数据知识，不把看教程当进度。
3. **实战线**先补人工复核和批次比较，再增加受限的多步 Agent；每一阶段都要有可演示、可测试的产物。

## 一、当前基线

以下能力已在当前 `main` 代码中存在，不能再作为“从零待办”重复开发：

| 能力 | 当前实现 | 结论 |
| --- | --- | --- |
| 桌面应用 | Tauri 2 + React 19 + TypeScript + Vite | 主技术路线已建立 |
| 实时采集 | 相机枚举、预览、拍照、停止与切换 | 已有真实物理数据入口 |
| 视觉表型 | YOLO 推理、检测框、置信度、按类别聚合 | 已能形成表型记录 |
| 数据存储 | SQLite 保存会话、消息、照片、表型和工具日志 | 已有本地事实源 |
| 批次组织 | `photos.batch_label`、批次选择、照片检索 | 已有最小组织维度 |
| 数据导出 | 按“批次 × 类别”汇总并导出 CSV | 已有非 LLM 交付物 |
| Agent 工具 | `query_phenotypes`、`search_photos` | 人类和 LLM 共用工具入口 |
| LLM 闭环 | SSE 流式响应、thinking、单轮 tool calling、结果回填 | 是受限工具助手，不是多步自主 Agent |
| 可追溯性 | `tool_call_log` 记录调用方、参数、结果与错误 | 工具层已有审计基础 |
| 数据可信提示 | `n_low`、`n_high`、`reviewed` 字段与提示词约束 | 有标记，但缺少真正的人工复核写入流程 |
| 相机错误 | channel 错误事件与 `data/logs/camera_errors.jsonl` | 有基础错误反馈，仍需场景化验证 |

当前最大缺口不是“再加一个聊天功能”，而是：

- `reviewed` 默认写入 `false`，没有完成“人工纠正 → 保存真值 → 分析使用真值”的闭环。
- 现有工具擅长查询单条/列表，尚不能给出可复现的批次对比、异常筛查和证据引用。
- LLM 只能执行一次工具调用；复杂育种问题还不能以受控步骤完成。
- 尚无真实育种人员、真实批次和最终交付 Excel 对 Demo 的有效性进行验证。

## 二、目标线

### 2.1 北极星目标

让育种人员完成一次从采集到分析的任务：

> 选择一个育种批次，连续采集作物图像，自动提取表型；人工快速复核关键结果；系统按批次比较并给出带原始照片、统计口径和不确定性说明的分析结论；整个过程可回看、可导出，断网时采集和复核仍可工作。

这里的“自主”不是允许模型自由操作所有能力，而是：在用户给出明确任务后，Agent 能在授权工具、步骤预算和数据边界内自行完成查询、比较、证据整理与总结；高风险结论和数据修改仍需人工确认。

### 2.2 初代 Demo 必须完成

1. 用户创建或选择批次标签并启动相机。
2. 系统持续预览，可选择启用 YOLO；无模型或推理失败不应中断基础拍照。
3. 拍照后保存原图、检测结果和表型聚合，并明确显示低置信结果。
4. 用户能确认、纠正或拒绝表型数量，形成可区分的人工真值。
5. 用户提出“比较 A、B 两批某类表型”的问题时，Agent 调用确定性统计工具，而不是自行计算或臆测。
6. 结果包含样本量、统计口径、低置信/未复核数量以及可点击的证据照片。
7. 用户可导出与界面统计一致的 CSV；核心采集、复核和导出不依赖 LLM 在线。
8. 工具调用、失败与最终结果可在历史中回看。

### 2.3 Demo 验收指标

| 维度 | 最低验收线 |
| --- | --- |
| 完整性 | 使用预置样例或真实相机完成一次“采集 → 复核 → 对比 → 导出” |
| 一致性 | 页面、Agent 工具和 CSV 对同一数据集给出相同聚合结果 |
| 可信度 | 未复核或低样本结论必须明确提示，不能输出确定性育种决策 |
| 可追溯 | 每个分析结论能回到工具参数、工具结果和相关照片 |
| 失败恢复 | LLM 断网不影响采集/复核/导出；YOLO 失败不阻断普通拍照 |
| 性能 | 相机预览保持可操作；具体帧率与推理延迟在目标设备实测后固化 |

### 2.4 明确排除

初代 Demo 不做：通用多智能体平台、开放式自主修改数据、育种知识 RAG、复杂实验设计实体、全自动育种决策、本地大模型训练、多相机编排、为了“纯 Rust”重写已经稳定的第三方能力。

## 三、理论学习线

理论学习采用“问题驱动 + 代码映射”。每个主题以能解释、修改和测试仓库中的一段真实代码为完成标准。

### 3.1 Rust：只学马上会遇到的核心

| 主题 | 对应项目问题 | 学习产出 |
| --- | --- | --- |
| 所有权、借用、生命周期 | 相机帧、SQLite 连接、模型句柄如何安全传递 | 能解释 `Arc<Mutex<Option<...>>>` 的所有权关系 |
| `struct`、`enum`、模式匹配 | `CameraEvent`、DTO、错误状态 | 能新增一个有测试的事件或 DTO |
| `Option`、`Result` 与 `?` | 相机/文件/网络/DB 错误 | 能把失败路径变成结构化错误而非 `unwrap` |
| Trait、泛型与模块 | 推理模型、工具与序列化边界 | 能读懂现有 crate API，不急于自建抽象 |
| 线程、channel、`Arc`、`Mutex` | pump、YOLO 推理和 Tauri 状态 | 能说明锁范围、背压和退出回收风险 |
| async/await 与 Tokio | LLM HTTP、SSE 流 | 能解释异步等待与 CPU 并行的区别 |
| Cargo、测试、Clippy | 依赖与质量门 | 能运行并理解项目的最小验证命令 |

入门可浏览[菜鸟 Rust 教程](https://www.runoob.com/rust/rust-tutorial.html)，涉及所有权、并发、异步和工程实践时以[《The Rust Programming Language》](https://doc.rust-lang.org/book/)和 crate 官方文档为准。Rust 不是第一门语言时可先用 Python 理解变量、函数、集合、异常和模块；已有 TypeScript/Python 基础则不需要重新从 Python 起步。

### 3.2 Tauri：理解边界而非只会调用命令

重点掌握：Windows 前置依赖、Tauri 进程模型、command、事件、channel、State、capabilities、路径与资源生命周期。当前 Windows 环境已经能识别 Node、npm、Rust、Cargo 和 `stable-x86_64-pc-windows-msvc`；正式开发仍以一次真实构建和应用启动作为最终环境验收。[Tauri 官方前置条件](https://tauri.app/start/prerequisites/)指出 Windows 还依赖 Microsoft C++ Build Tools 和 WebView2。

### 3.3 Agent：借鉴 Pi 的最小内核

[Pi](https://github.com/earendil-works/pi)值得参考的是分层而不是代码语言：

- 多模型协议层与 Agent runtime 分离。
- Agent loop 维护消息状态，模型输出工具调用，执行结果再进入下一步。
- 工具拥有明确名称、输入 schema、执行结果和错误。
- 核心保持最小，把权限、计划模式、子 Agent 等作为可选扩展。
- 事件流与状态可被 UI、脚本或 RPC 适配器消费。

Pod Agent 应先实现领域受限版本：`model adapter → agent runner → typed tool registry → run/step events → persistence`，而不是复制编码 Agent 的 shell、文件编辑器、MCP 和子 Agent 功能。

### 3.4 oh-my-pi：参考高性能边界，不照搬体量

当前 [oh-my-pi](https://github.com/can1357/oh-my-pi) 不是纯 Rust Agent 重构：其 `pi-agent-core`、`pi-ai` 与主要应用仍以 TypeScript 包组织，Rust crates 主要提供 shell、PTY、AST、文件遍历、隔离、音频等原生能力。对本项目的有效启发是：

- 把高频、CPU 密集、系统相关能力放在 Rust 边界。
- Agent 编排保持清晰、可替换，不因追求性能提前复杂化。
- 性能改造必须有基准，而不是把“使用 Rust”本身当验收结果。

### 3.5 育种与表型数据

在增加“育种分析”前必须补齐最小领域知识：实验单位（材料、家系、小区、重复）、表型定义与单位、采样协议、缺失值、环境与批次效应、人工真值、统计比较和不确定性。完成标准不是读完概念，而是拿到至少一份真实工作流和最终 Excel，能够定义一个不会混淆“照片批次”与“育种实验单位”的数据字典。

教学视频可作为从零实现 Agent 的直观补充：[Bilibili：BV1jbXKBGECC](https://www.bilibili.com/video/BV1jbXKBGECC)。视频中的框架选择不自动成为本项目决策依据。

## 四、实战线

### 阶段 0：基线与可复现环境

状态：大部分已完成。

- 固定开发分支并保留 `main` 对照。
- 记录 Node、npm、Rust、Cargo 和 MSVC target 版本。
- 完成依赖安装、类型检查、Rust 检查和一次 Tauri 启动。
- 准备不含隐私的最小样例图片/数据库，使无相机测试可复现。

退出条件：新开发者可以按文档启动项目，测试失败能区分代码问题、模型缺失与硬件缺失。

### 阶段 1：数据真值闭环

这是下一阶段的最高优先级。

1. 先写设计文档，定义“确认、纠正、拒绝”的语义和不可变原始检测数据。
2. 明确是否增加 `corrected_count`、复核时间和复核来源；数据模型变化须先确认。
3. 新增 Rust command 与纯函数测试，保证复核操作可追溯且可重复读取。
4. 在照片详情/表型面板提供最小复核 UI。
5. 让查询与导出同时返回模型值和人工值，并定义聚合优先级。

退出条件：至少一条表型记录能被人工纠正，重新打开应用后仍保留；Agent 与 CSV 使用相同的“有效值”规则。

### 阶段 2：确定性育种分析工具

- 增加 `compare_batches` 一类纯统计工具，输入明确的批次、类别与指标，输出样本量、差异、置信数据和证据照片 ID。
- 工具先供人类在 Tools 页面直接调用，再开放给 LLM。
- 所有计算由 Rust/SQL 或经批准的 Python 原型完成；LLM 只负责选择工具和解释结果。
- 真实育种实验单位未验证前继续使用 `batch_label`，不提前建立 `plots` 等领域实体。

退出条件：相同输入重复运行得到相同 JSON，页面与 LLM 对该 JSON 的解释可核对。

### 阶段 3：受限多步 Agent

仅当阶段 2 出现一个必须串联两个以上工具的真实任务后启动。

- 引入独立 `AgentRunner`，把模型协议、工具注册、循环策略和 Tauri 事件分开。
- 每步设置最大工具数、最大轮数、超时、取消与结果大小限制。
- 数据修改类工具默认需要人工确认；未知工具和参数校验失败立即停止。
- 出现真实多步回放需求后再增加 `agent_runs` / `agent_steps`，不提前建空表。
- UI 展示“计划/调用/观察/完成”，但不把模型私有思维过程当作可靠审计证据。

退出条件：Agent 能完成一个经批准的“查询两个批次 → 统计比较 → 找到证据照片 → 形成有边界总结”任务，并能在任一步取消和回放工具事实。

### 阶段 4：真实场景验证

- 带稳定 Demo 找 2–3 名真实育种人员观察其拍照、命名、归属、复核和汇总流程。
- 收集他们实际使用的脱敏 Excel、字段单位、错误补救方法和交付标准。
- 用真实任务验证：哪些步骤值得 Agent 自动化，哪些必须保留人工判断。
- 根据证据决定是否引入材料/小区/重复实体、知识库、离线模型或更完整的 Agent loop。

退出条件：至少一个真实任务成功完成，并记录失败点、节省时间、数据错误和用户是否采纳结论。

## 五、Python/FastAPI 与 Rust 的决策

当前不建议把已有 Rust 后端改成 FastAPI：相机、YOLO、SQLite、Tauri IPC 和工具调用主链已经存在，迁移会产生双写、进程管理和打包成本，却不能验证新的用户价值。

Python 的合理位置是**隔离的实验能力**，例如新统计方法、模型推理或快速变化的育种算法。采用流程：

```text
定义稳定输入输出 → Python 原型与样例评测 → 验证用户价值和性能 → 决定淘汰/保留 sidecar/迁移 Rust
```

只有当原型进入稳定主链、部署体积或性能成为可测问题时才重写 Rust。Rust 重写必须复用同一组契约测试和样例数据，证明行为等价。

## 六、下一项建议任务

先讨论并编写“表型人工复核闭环”设计，不直接开始多步 Agent。设计至少回答：

1. 原始 YOLO 结果是否永远保留，人工值如何与其并存？
2. 复核粒度是整张照片、类别聚合，还是单个检测框？
3. 导出和 Agent 分析优先使用哪个值，如何显示差异？
4. 谁、何时、基于哪张图完成复核，如何撤销或再次修订？
5. 旧数据库如何迁移，未复核记录如何兼容？

该设计确认后再拆成 schema、Rust command、前端 UI、工具查询与迁移测试五个小任务。

## 七、工作流与提交边界

- 每个阶段遵循“讨论/设计 → 实现 → 验证 → 精准提交”的顺序。
- 当前开发分支与 `main` 指向同一基线提交，后续本地提交后可用 `git diff main...HEAD` 对比。
- `docs/git-branch-quickstart.md` 是进入本次任务前已存在的未跟踪文件，不应混入其他提交。
- 推送开发分支前再次检查目标远程、提交内容、验证结果和敏感文件，并取得工程师明确确认。
