## 主持人开场

我们要决定 Pod Agent 的 **agent 开发方向**。先锁定事实锚点，避免空谈：

- 项目定位"以智能体为核心"，但 `agent.rs` 是 **0 行空文件**；现在的"智能体"只是一个带历史消息的 OpenAI 兼容流式聊天补全封装——**没有 tool calling、没有规划循环、没有 RAG**。
- 但相机这条主线极成熟：实时取流 + YOLOv8 同步推理 + 表型聚合（count/confidence/面积）落 SQLite，4 张表（sessions/messages/photos/phenotypes）已就位。
- LLM 走远程 HTTP，`config.json` 已有多 provider 抽象；单人开发，14 天 47 个 commit，节奏快。

**核心张力有三条**：
1. **方向之争**——工具型 agent（让 LLM 驱动已有的相机/YOLO/DB 强能力）vs RAG 检索型（拿 phenotypes 表做育种数据问答）vs 渐进增强（先做记忆/上下文，暂不引工具）。
2. **领域锚点**——育种 agent 不该退化成通用 chatbot，`phenotypes` 表才是金矿。
3. **复杂度边界**——单人开发，完整 tool loop 是否过度？function calling 在 DeepSeek/通义/OpenAI 间支持参差，多 provider 架构是否要为 agent 收敛？

## 第一轮：各抒己见

### 架构师 (Architect)

我明确支持**渐进增强方向，且第一步就锚在 phenotypes 表上做受限工具型 agent**。不是纯 RAG，也不是上来就全套 tool loop。

理由很实在——架构上要优先让"已沉没的成本"产生复利。你们已经付了最大的代价：YOLO 推理闭环 + 坐标映射 + 表型聚合落库。这套数据不是辅助材料，是育种领域的核心资产。所以 agent 第一笔投入就该让它能**回答 phenotypes 上的问题**，而不是去检索文档或调外部 API。具体形态：暴露 2-3 个受限工具（`query_phenotypes(class, date_range, agg)`、`list_photos(detections_filter)`、`compare_groups`），让 LLM 通过 function call 把用户的自然语言问题转成对已有 SQLite 的结构化查询，再用表格/图表回答。

为什么不上完整 tool loop：单人开发 + 14 天 47 commit 的节奏，意味着每多一层抽象都是维护负担，而且全局用 String 错误类型、`agent.rs` 还是空文件——地基没到支撑复杂 agent 的密度。先做"单轮 function call + 一次查询 + 渲染结果"，这是 50 行级别的闭环。

为什么不是纯 RAG：育种数据是结构化的，强行切块向量化是反模式，SQL + 聚合才是对的工具。

核心一句话：**先让 agent 学会"读自己的表"，再谈规划和多步推理。**

### 编程手 (Programmer)

确认完毕。send.rs 的 SSE 解析是 line-by-line 字符串拼接，跨 chunk 边界会断行——这是已存在的 bug。关键现状：tool calling 零基础设施，messages 表只有 role/content/thinking，没有 tool_calls 字段，error 全是 String。

**第一步只做"单工具 + 单轮"，不做 agent loop。** 别上来就搞 ReAct loop、tool registry、上下文窗口管理那一套。单人 + Rust + String 错误满天飞的状态下，那是给自己挖坟。坑最少、最快能跑起来的是给现有 `send_llm_message` 加一个"拍照统计"工具，让模型能查 phenotypes 表。理由：

1. **provider 兼容是死结**。DeepSeek-V3 的 tool_calls 在 delta 里是分片数组，通义工具名带中划线会报错、参数 JSON 时字时对象。现有 send.rs 根本没解析 tool_calls 分片累加。必须先重写成按 index 累积。
2. **messages 表要扩列**。tool calling 需要 tool_calls/tool_call_id/role='tool' 三种新形态。
3. **错误类型必须先补**。否则 loop 不可调试——分不清"网络断了"和"模型瞎编工具名"。

落地顺序：(1) error.rs 写 LlmError enum；(2) messages 加列；(3) 注册一个 query_phenotype_stats 工具；(4) SSE 解析重写。**单轮、单工具、同步执行**，跑通再说 loop。RAG 直接否掉——杀鸡用牛刀。

### 建模手 (Modeler)

**核心立场：现有 4 张表是"会话 + 成像产物"，缺的不是更多表，是 agent 的"行动轨迹表"。** 现在的数据只回答了"用户说了什么、拍到了什么"，从不回答"agent 想做什么、做了什么、结果如何"。一个真正以智能体为核心的系统，数据层必须能形式化表达 agent 的 reasoning–acting–observation 闭环。

**新表最小集：**
1. `agent_runs` — 一次完整 agent 执行（id、session_id、user_intent、status、token_usage）。
2. `agent_steps` — run 内每一步（id、run_id、step_type ∈ {thought, tool_call, tool_result, observation}、payload JSON、parent_step_id）。

**RAG vs 工具型的建模差异：**
- **工具型（DB 查询工具）**：数据已在结构化表里，agent 发起 SQL/谓词查询。建模上工具调用是 agent_steps 里的一行 tool_call。**数据不动，agent 动。** 最低成本路径。
- **RAG 检索型**：需把非结构化育种知识向量化，新增 knowledge_chunks 表 + 向量索引。语义完全不同：RAG 核心实体是"知识块"而非"行动"，与 agent_runs 正交，不替代。

**判断：育种 agent 第一价值燃料是 phenotypes 表，不是 RAG。** 工具型 agent 让 LLM 用自然语言驱动 SQL，投入产出比远高于先建向量库。RAG 留给"非结构化育种知识问答"明确边界内。

**一句话：先加 agent_runs + agent_steps 两张表撑起 agent 闭环，让 phenotypes 成为第一个被 agent 调用的数据工具；RAG 作为知识库独立建模，与 run/step 正交。现有 4 张表不够，但缺口精准——缺的是"行动"，不是"知识"。**

### 恶魔 (Devil's Advocate)

事实核验完毕。`agent.rs` 确实是 0 字节空文件，置信度直接 `unwrap_or(0.0)` 进 SQLite，LLM 全程裸同步流式，零重试零超时。你们这群"agent 专家"最可能犯的五个致命错误：

**错误一：标签驱动开发——为了"叫 agent"而造 agent。** 你们不是在做 agent，是在给一个 curl 调用披狼皮。把空文件夹填满，不会让它变聪明。

**错误二：幸存者偏差照搬 LangChain/AutoGPT 架构。** 那些 demo 活下来是因为有人在 Twitter 上筛过了几千个烧光 token 的失败案例。引入多 agent 编排、记忆层——死法会是三个月后变成无人维护的僵尸抽象层。

**错误三：虚假二分法——"工具型 vs RAG"对立。** 冲突的是你们根本没定义清楚：育种员到底要问什么？没需求就开始选架构，是在给锤子配三种不同的指甲刀。

**错误四：把概率性脏数据当事实喂给 LLM——最阴险的。** `confidence.unwrap_or(0.0)` 照样入库，YOLO 把土块识别成果荚，聚合出 avg_confidence=0.72 的"表型数据"，让 LLM 基于幻觉做育种建议？**LLM 不会质疑输入，它会用最自信的语气告诉你一个基于幻觉的幻觉。这是造谣机器。**

**错误五：无视远程 LLM 在桌面育种场景的灾难性延迟/成本。** 温室、田间网络是奢侈品。SSE 裸流零超时，断网就无限挂起。育种员等 30 秒才有第一个字，他第二次就只用本地相册了。**agent 还没跑起来，用户先跑光了。**

先回答三个问题再谈架构：**育种员每天最高频的 3 个问题是什么？断网时系统能不能活？YOLO 的置信度低于多少就该丢弃而不是聚合？**

## 第二轮：激烈交锋

### 架构师 (Architect)

**针对 (A) 延后，不为单人项目加 agent_runs/steps。** 现在连第一个 tool call 都没跑通，建 step_type 轨迹表等于给不存在的执行循环建模。单轮 function call 的轨迹天然落在 messages 流里（user→assistant(tool_calls)→tool→assistant），这是 OpenAI 协议本身的表达能力，零额外表。取舍：messages 加两列扛住第一阶段。等出现"育种员抱怨 agent 第三步走错了，我想回看它当时怎么想的"——这种可观测性需求真实出现时，再加 agent_runs。

**针对 (C) 接受攻击，但门槛放对层。** 恶魔的脏数据攻击成立，地基有裂缝。但我不同意因此推翻 phenotypes 优先，问题在质量门槛的位置。分两层：
1. **写入门槛（最关键）**：聚合写库前按 class 做置信度过滤，`min_confidence_per_class` 配置表默认 0.5。脏数据在门口挡掉。这一步比 agent 本身更重要。
2. **读取门槛（兜底）**：`query_phenotype_stats` 返回时附带样本数 n 和置信度区间，工具描述写明"当 n<阈值或 avg_conf<阈值时数据不可靠"。让 LLM 看到不确定性。

**强烈不同意恶魔**：把需求验证和架构讨论对立起来我不同意。需求验证和数据质量是 agent 的前置依赖，不是替代品。不是"先验证需求所以别谈架构"，而是"验证需求和数据质量本身就是当前阶段的架构任务"。

点名建模手："缺的是行动不是知识"恰好论证了**先别建模行动表**。既然缺的是行动本身，就先让 agent 产生第一个行动，等行动真实发生且需要回溯时再建表。Schema 跟着行为长，不是行为迁就 schema。

### 编程手 (Programmer)

**针对 (A) 现在加是过度。** 建模手的两张表是 ReAct 多步推理的物理载体。但我们第一版只做单轮单工具，整个链路 messages 表加两列就能完整承载——thought/observation 在单轮里根本没有持久化需求。这两张表第一版只会空转。YAGNI，明确。

**针对 (C) 这部分让步。** 落地三步：①phenotypes 表加 `filter_confidence REAL` 列记录过滤阈值；②media.rs 聚合时默认丢掉 confidence<0.5 的 detection（阈值常量化）；③tool 返回结果时携带 included/total 计数，让 LLM 知道丢了多少低置信样本。

**最不同意架构师**：他说"否 RAG"当决策点，但 query_phenotype_stats 单工具返回结构化聚合 JSON，这根本不是 RAG 的应用场景，拿"否 RAG"当决策点是打稻草人——RAG 本来就不在单工具路径上，否不否没差别。

### 建模手 (Modeler)

**(A) 让步。** messages 表能扛单工具是对的。但判据必须现在钉死，出现以下任一信号立刻加表：①第二个工具注册；②多步推理；③需要回放/审计某次决策的中间状态。在此之前把 thought/tool_call 塞进 messages.content 的约定先写死，迁移成本就一行 ALTER。

**(C) 恶魔是对的，地基在晃。** 但解法不是加"数据质量列"——那是元数据创可贴。真正的建模缺陷是 **avg/min/max_confidence 三个标量把分布压扁了**。YOLO 误识别土块 confidence=0.3，混进 10 个真果荚(0.9)后 avg=0.84，幻觉被平均掉了。应改为 `confidence_dist JSON`（直方图或百分位），让 LLM 自己看见"这批里有个 0.3 的离群"。再补 `reviewed BOOLEAN DEFAULT 0`——人工标过的行才进决策上下文。

**(B) 苏格拉底问到点子上。** 现阶段 agent 该建模成**统计查询器**，不是决策辅助器。决策需要产量、家系、多年重复等 phenotypes 表根本没有的维度，现在做决策必然是 LLM 脑补。查询器是可验证的，决策器在脏数据上不可验证。

**强烈不同意编程手**：messages 加 tool_call_id 没问题，但"重写 SSE 解析"放到第一步会埋雷——tool_call 的 delta 协议和 content 流是两种形态，混进同一解析器会让 reasoning 模型和 function call 互相打架。应该单独写 `parse_tool_call_stream`，原解析器不动。

## 第三轮：最终辩护

### 架构师 (Architect)

**① 做不做 agent？做。但顺序是「先修脏数据，同 PR 出 agent.rs 单轮查询器」。** 恶魔的否决我接受一半：脏数据必须先修。但我否决"修完就停"——单人开发，没 agent 闭环，data 系列表型数据的 ROI 永远收不回来。折中判据：修脏数据和 agent.rs 第一个 query_phenotypes 工具合并为**一个语义单元**提交，因为「写入门槛」和「读取门槛」本就是同一套置信度策略的两面。

**② 脏数据方案：让步，接受恶魔的 Option<f32> + 建模手的 reviewed BOOLEAN。否决自己的 per-class 阈值配置表。** 理由：per-class 阈值配置是过度设计——单人单品种没有"配置真正在变"的证据。Option<f32> 是最小语义正确解。reviewed 给了人工回溯钩子，零运行时成本。

**③ 苏格拉底锤的回答：agent 相对 Excel 的本质区别不是「敢说我不确定」，而是「跨表的因果追问」。** Excel 能查"这张照片检测到几个荚"。agent 的差异化是回答"这批比上周那批少 30%，原因是光照还是品种"——需要横跨 photos/phenotypes/messages + 时间维度 + 调用 LLM 推理的闭环。

**最终 actionable 3 步：** (1) phenotypes.avg_confidence 改 Option<f32>，加 reviewed BOOLEAN，media.rs count=0 返回 None；(2) agent.rs 单工具 query_phenotypes，系统提示强制"数据未 reviewed 时标注"；(3) 暂停观察，agent_runs/steps 等需求真实触发再加。

### 编程手 (Programmer)

事实核对：media.rs:241 `count=0 → avg=0.0`，min/max 用 `INFINITY/NEG_INFINITY` 写进 REAL 列（**这是更隐蔽的脏数据，恶魔没提**）；send.rs 186 行无 tool_call。

**① 第一版做不做 agent——做，但脏数据先修再上，不并行。** 恶魔把"先修脏数据"排在前面，这次我认。工程阻塞：send.rs 要新增 tool_call 持久化、media.rs 聚合要喂给 tool，这两个入口都踩在脏数据上。排序：1.修脏数据（半天）→ 2.messages 加两列 → 3.重写 SSE（单独 parse_tool_call_stream，不碰原解析器）→ 4.注册 query_phenotype_stats → 5.跑通最小闭环。error.rs 撤一步：send.rs 里就近加 LlmError 三变体够了。

**② 站 filter_confidence 列 + media.rs 聚合丢 <0.5 + tool 返回 included/total。** confidence_dist JSON 直方图，单人项目不值（30 行序列化 + 前端图表面板，YAGNI）。最小修法：拍照时 dets.filter(|d| confidence>=0.5) 后再聚合，空集 min/max 给 None/NULL 而不是 ±INFINITY。

**③ 配叫 agent 的判据——敢说"我不确定，我去查"。** RPC 套壳 vs agent 的可验证分界线有三条，第一版必须过至少一条：**触发**（模型自主决定要不要调 tool）/ **拒绝**（tool 返回空/异常时模型回"没找到符合条件的记录"）/ **条件**（能基于上一轮 tool 结果决定下一步，历史里带 tool_call_id）。第一版过"触发+拒绝"两条即可。做不到就是 RPC，承认它是 RPC 也行，别叫 agent。

### 建模手 (Modeler)

**① 排序：先修脏数据，但不是"别做 agent"。** 把这两件事对立是假二分。真相：脏数据修复**就是**第一版 agent 的全部内容。confidence_dist 和 reviewed 加进 phenotypes 表的那一刻，agent 的"查询器形态"就已落地——它能回答"这批数据可信吗""哪些 class 还没人工复核"。排序：**先建模，后行动；建模即第一版 agent**。

**② confidence_dist 让步，reviewed 不让。** 恶魔的 Option<f32>/quality_flag 是给标量打补丁，没解决"0.3 离群被 0.9 平均成 0.84"的信息丢失。编程手的 filter_confidence 列更糟，把决策逻辑焊死在表里。但 confidence_dist JSON 对单人项目确实重。折中：**保留 reviewed BOOLEAN**（零维护成本，是 agent"敢说我不确定"的物理载体），confidence_dist **降级为 n_low/n_high 两个 INT**（低于 0.5 和高于 0.8 的检测点数）。脏值一眼可见，无需 JSON 解析。

**③ 查询器凭什么叫 agent。** 区别不在自然语言接口——那是 Excel+LLM 也能做的。区别在 **reviewed 这个维度让 agent 能拒绝回答**。Excel 的 SUMIFS 永远返回一个数；带 reviewed 的查询器能说"这个 class 只有 3 个检测点、0 个复核过，结论不可信"。reviewed=0 是数据建模层面的"不确定性原语"——它把"我不确定"从 LLM 的口癖变成可查询的字段。这就是 agent 相对 Excel 的全部差异化。

**最小路径**：phenotypes 加 reviewed + n_low + n_high 三列；media.rs count=0 → reviewed 强制 0、n_low/n_high=NULL；前端给 reviewed 加人工勾选入口。agent.rs 保持 0 行，等这三列被查询语义用满（出现第二个工具调用），再开 agent_steps 表。

## 主持人总结

### 共识点

1. **第一版 agent = 单工具单轮查询器**。无人支持 ReAct loop / agent_runs+steps（建模手三判据：第二个工具/多步推理/需回放审计出现才加）。

1. **脏数据修复深度**：恶魔/架构师要最小 `Option<f32>`；编程手加 `filter`+丢<0.5；建模手要 `n_low/n_high` 离散计数。三者可叠加，但一次做多少未定。

3. **agent vs Excel 的定义三说**：架构师=跨表因果追问；建模手=reviewed 维度的拒绝回答；编程手=模型自主触发+拒绝空结果。定义未统一。

## 第一轮：各抒己见

### 架构师（Architect）

核心立场：**纵深优先，方向是「批量批处理 + 报告导出」这条生产线，agent 天花板暂时不破，YOLO 架构债先别动。**

- **纵深就是"从单株拍照 → 田间批量 → 出报告"价值链**。现在 MVP 的价值终点是"phenotypes 表里一行 JSON"，对育种工作者是半成品。真正闭环终点是"今天这 50 株的表型报告 PDF/Excel"。批量处理 + 报告导出是确定性功能（无 AI 不确定性、无外部 API 依赖、复用已有 phenotypes 表），边际成本最低、价值跃迁最大。
- **agent 天花板**：维持单轮单工具 YAGNI，但把第二个工具定义为"报告生成"而非"多步推理"。真正该加的第二个工具是 `generate_report(date_range, classes)`——让 LLM 从"查数据"升级到"产报告"，仍是单轮硬约束。
- **架构债**：pump 回调里同步 YOLO + Arc<Mutex> 现在不动。理由：单相机、每 N 帧、本地 ONNX（几十 ms 量级）。批量批处理是离线 YOLO 模式（读图→推理→写表），天然绕开 pump 同步问题——用新增路径消化债务比原地重构便宜。

一句话判断：下一步把工程力气压在「批量导入照片 → 离线 YOLO → 表型聚合 → 报告导出 → LLM 一键生成报告」，agent 维度只加一个 generate_report 工具，YOLO pump 架构不动。

### 编程手（Programmer）

核心立场：**下一步做"纵深 + agent 一层楼"，不该碰"横向扩面和架构大改"。**

**判断为过度工程（现在碰是烧时间）：**
1. agent_runs/steps 表 + ReAct 循环——成本至少一周，收益在真实育种场景看不出来。加第二个工具的信号是"LLM 自己想调却没有"，不是"agent 叙事不够"。
2. 数据看板 / 报告导出全家桶——育种要的是表格+几张图，不是 BI 仪表盘。phenotypes 表已有聚合，前端 DataTable + 导出 CSV/Excel 按钮半天落地。
3. 多相机支持——等于重写相机子系统，YAGNI。
4. YOLO 异步化重构——没坏别修。

**值得现在做的实在活：**
1. 第二个工具：`list_photos` 或 `get_photo_detail`——让 LLM 能回答"给我看看置信度最低的那张"。照着 query_phenotypes 结构复用，一个语义单元能落地。
2. 批量照片处理"最小版"——phenotypes 加 `batch_id` 或按 `captured_at` 时间窗口 GROUP BY 查询。
3. pump 回调边界兜底——模型 None 时静默跳过、推理超时兜底、Mutex 拿不到锁退避。

一句话：别为"agent 是核心叙事"这个帽子去加 ReAct 循环，也别为"走向产品"去做看板。真实信号是"LLM 还想查什么但查不了"——补第二个工具；真实场景是"一批照片怎么聚合"——补时间窗口查询。其他全部 hold。

### 建模手（Modeler）

核心立场：**先把"表型是一张快照"这个根本隐喻改掉。**

现在的 `phenotypes` 表在领域建模上是**退化的一阶快照**——一行就是"某张照片里某 class_name 的统计"。回答得了"这张照片几个穗"，回答不了任何真正的育种问题：

- **缺时间维度**：育种核心是纵向追踪——同一株/同一小区从苗期到成熟。现在只有 created_at 单点，没有"植株/小区（plot）"稳定身份，跨照片对不上。
- **缺实验设计轴**：没有 variety/batch/plot/site/treatment 任何因子。育种统计本质是组间对照，"按品种比产量"在当前模型下做不出来。
- **缺品质之外的真值通道**：n_low/n_high/reviewed 诚实暴露了"AI 计数有多脏"，但人工真值没有一席之地——reviewed 只是个布尔，没有 reviewer/reviewed_at/corrected_count。

下一步建模重点：引入 `plots`（小区，含 variety/batch/site/treatment 外键）作为聚合根，photos 通过 plot_id 挂到稳定身份，phenotypes 加 corrected_count/reviewed_by/reviewed_at，AI 预测与人工真值并存可对账。**表型的领域本质是"对同一观测单元的多次观测"，不是"对一张照片的统计"——这个隐喻不换，上层 agent 都是沙上建塔。**

### 体验者（UX Specialist）

核心立场：**当前流程跟育种工作者真实工作节奏是错位的。**

育种工作者在地里一天拍几百上千张，走一遍小区、每个小区拍一组。拍完后做非常具体的事——**按小区/家系/品种聚合，统计数量、合格率、变异范围，导出一张表附在课题报告或田间记录表里交上去**。痛点排序很清楚：

1. **没有"批"的概念**：照片是散的，没有小区/家系/处理归属。拍了 200 张，系统不知道哪几张属"小区 A-3"。这是从"拍照玩具"到"育种工具"的生死线。
2. **导出是刚需**："拍一张→存一条→对话问一句"是工程师视角炫技，育种工作者真正交差要的是 Excel/报告。
3. **reviewed/n_low/n_high 埋了但用户碰不到**：心里清楚"人工复核修正自动统计"是关键，但当前 UI 没有让人核对修正标注。育种数据要进论文、报奖、申报品种权，错一个数字都是事故。

立场：下一步往"批量 + 聚合 + 导出 + 复核"使劲，不是继续给对话加工具。agent 单轮单工具现在够用，真正卡住用户的是没有"任务/批次/小区"这层数据语义。

### 恶魔（Devil's Advocate）

**罪一：用"agent"这个名字反向定义需求（名称即论证）。** "项目叫 Pod Agent 所以必须把 agent 做深"——命名是市场行为不是技术约束。被三个字母绑架，名字改一行，架构债背半年。该问"用户愿不愿为多步推理付费"。

**罪二：纵深 vs 广度的虚假二分法。** 真正第三选项你们不敢提：**当前哪条都没跑通到"育种员每天用"的程度**。MVP 跑通 ≠ 有人用。0 真实日活用户前提下讨论方向，是在给不存在的市场优化。先去田间蹲三天看育种员用什么 Excel，比排兵布阵值钱十倍。

**罪三：追逐时髦技术（YOLO 异步化、RAG、多模态）。** "pump 同步推理是债得改异步"——是债没错，但你们有证据它现在卡用户了吗？FPS 掉到多少？丢帧率多少？没数据就重构，是为技术而技术。

**罪四：自动出报告 vs 对话助手——又一个伪二分法。** 这俩可能是同一个东西的两层皮：对话是输入界面，报告是输出格式。真正张力被你们藏起来了：**LLM 的不可替代价值到底在哪？** 如果只是 summarize phenotypes 表，SQL+模板就够，LLM 是套壳。除非能做育种员做不到的事（跨照片趋势判断、异常株定位、育种决策建议）。

**罪五：把"昨天已归档"当结论（路径依赖谬误）。** 单轮单工具 YAGNI 的判定，在"真实需求"未验证前提下做出，本身建立在沙子上。YAGNI 是对的，但理由是"暂时不需要"不是"永远不需要"。

## 第二轮：激烈交锋

### 架构师（Architect）

### 建模手（Modeler）

**诚实收缩 plots。** 第一轮的 variety/batch/plot/site/treatment 五轴确实太重，那是 ERP 不是 MVP。最小必要模型只要两样：**稳定的聚合身份** + **真值通道**。落地就一张表 `plots(id, code, created_at)`——code 是用户给的人话标签（"A区-3号棚"），photos 加可空 plot_id 外键。体验者要的"小区归属"一个下拉选 plot_code 就满足，不需要 variety/家系/处理这种实验设计元数据。批的概念用 batch_id 软分组（按时间窗口或手动归并），不建表。

**苏格拉底正中靶心。** "表型字段是育种需要还是 YOLO 恰好能给出"——答案是后者定义前者。class_name + count + confidence 完全是 YOLO 输出形状的投影，不是育种关心的性状（株高、叶面积、病害等级、结实率）。不是再加字段能修的，是**领域建模方向反了**。正解是先问育种员：这个小区你最终要比较什么？哪些数值得人工复核才进论文？AI 给的数你信到什么程度？

新论点：**信任分层。** AI 输出显式标记"未复核预测"，corrected_count 填了才升级为"可用数据"。LLM 价值不是 summarize 表，而是在用户问"这个棚这周结实率为什么偏低"时，能把 plot 维度、时间序列、异常照片拉到一起做归因——**跨实体关联推理才是 LLM 相对 SQL+模板的唯一护城河**。没有 plots 聚合根，LLM 连归因的坐标都没有。

### 建模手（Modeler）

**先认输。** 苏格拉底和恶魔是对的——plots 没有真实聚合对象时不叫聚合根。聚合根不是"占个位等着被填满"，定义要求它有不变量（invariant）、有生命周期、有被外部引用的一致性边界。当前一张照片都没被育种员看过、一个 plot 编号都没真人填过，这就是个**空集合上的投影**。之前把"应有的领域骨架"当成"已存在的聚合根"，是建模者的傲慢。

**争议 A 收敛：** 放弃"plots 聚合根"命名。改叫"**占位字段**"——只埋 schema，不立实体。

**争议 B 让步：** 数据模型不先于一切。先做导出拿反馈，但导出本身需要一个 GROUP BY 的 key——所以最小必要改动是编程手的 photos.batch_label TEXT（可空），不引入 plots 表。pump 稳定性优先级同意，没有稳定数据源，建模都是空中楼阁。

**争议 C 坚持：** LLM 护城河是跨实体关联推理，但**这个护城河要等真实关联存在才能兑现**。plots 没数据时，generate_report 只能是模板——这恰恰证明 LLM 当前没有存在理由的强制形式。接受结论：**当前 generate_report 走纯模板/弱 LLM，等 batch_label + corrected_count 真值通道铺满一个真实季再升级。**

**最小必要改动（建模手版本）：**
1. `photos.batch_label TEXT NULL`——唯一新增字段，零实体、零外键
2. `phenotypes.corrected_count INT NULL` / `reviewed_by TEXT NULL` / `reviewed_at TEXT NULL`——真值通道，可空，不破坏现有读路径
3. **坚决不碰：** plots 表、实验设计轴、agent_runs/steps 表、多轮 tool calling

**被什么说服了：** 苏格拉底那句"聚合根要有真实聚合对象"——领域建模第一性原理，绕开了。恶魔对"批量同音词"的拆解——把修辞伪共识钉死了。体验者"冻结开发做田野调研"——没有真实 plot 编号被真人填过，建的模就是自嗨。

建模的价值不是提前画 UML，是在真实数据长出来时给它合适的容器。当前数据还没长出来，先收手。

### 体验者（UX Specialist）

**争议 A 让步：** 恶魔和苏格拉底打中了。"批"是同音假象。放弃用"批"这个词，拆解成具体动作：**照片归属标签的录入流**——拍照瞬间能选到哪个小区/家系，并在导出时按它聚合。这就是真正关心的、可落地的 UX 动作。

**争议 B 折中：** 不坚持"冻结全部开发"。采纳架构师+编程手的方案：编程手先修 pump 错误路径（保稳定性），架构师先做顺序导出（拿反馈），这两件事**并行进行，不需要育种员在场**。只申请一条：**导出物长什么样，必须由我先用纸面原型走一遍"一个育种员收到这份报告会怎么用"**，不能直接进代码。这是 UX 唯一的硬约束。

**正面回应夹击——我凭什么是代言人？** 我不是。苏格拉底问得对：没见过这个育种员，产出合格标准从未被具体的人确认过。但**正因为如此，"先田野调研"才成立**——合理性不依赖于我正确，而依赖于"我们五个现在都在对着空气设计"。田野调研不是去验证我的脑补，是去戳破我们所有人的脑补，包括建模手的聚合根、架构师的报告导出、恶魔的"五罪"。没人验证的共识，是纸糊的。

**调研具体形态：** 找 2-3 个真实育种员（科研院所/育种基地，工程师负责联系），不问"你想要什么功能"，只做三件事：**看**他们现在怎么拍照、照片怎么命名、怎么归属到小区、最后怎么汇总成数据交差；**问**上一次照片搞混/丢失/归属错是什么时候、怎么补救的；**看**他们最终交出去的那张 Excel。产出标准：一份"现状照片归属与汇总工作流"记录，五个人对着它重新对齐。

**Actionable 建议：** 在导出功能动工前，先花半天在拍照界面加一个**自由文本标签输入框**（照片拍完即录，写进 photos 一个 label TEXT 列，暂不做结构化）。最小、零架构污染、能立刻给育种员试用的归属录入流——田野调研时直接拿它当调研道具，让育种员在真实小区里拍一张、标一句。它能产出**真实标签样本**，届时建模手的 plots 表、编程手的 batch_id、我的归属聚合，都能从真实样本里收敛出唯一答案，而不是五个人投票。

被说服的点：建模手的"真值通道必埋"和"信任分层"——即便照片归属标签，也必须区分"用户手填 vs YOLO 推断"，否则 LLM 日后无法跨实体推理。接受，写进 label 设计。

**回避问题的人：** 架构师。"generate_report 收敛为 LLM 解读归类+异常标注，证明没增量就砍成纯模板"——漂亮地绕过了争议 C 的核心：**如果 generate_report 被砍成纯模板，LLM 在这个项目还剩什么？** pump 不用 LLM，YOLO 不用 LLM，CRUD 不用 LLM，照片归属标签不用 LLM。砍掉报告解读后，LLM 唯一功能是"对话陪聊"——而陪聊是体验者自己承认的脑补。

**最终裁决（诚实 vs 自欺，0 真实用户前提下）：**

| 动作 | 性质 |
|------|------|
| 修 pump 错误路径、写复现测试 | **诚实**——锚定已存在的债务 |

**关于 LLM 的存废：** 诚实的答案是——**当前 LLM 在 Pod Agent 中没有不可替代的护城河**。建模手说"跨实体关联推理"是护城河，但护城河需要实体。现在实体只有 photos/messages/phenotypes 三张表，关联稀薄到 LLM 一条 SQL 就能替代。**不要为了保留 LLM 而发明需求。** 如果田野验证后发现育种员真的需要"帮我看看这批苗哪些长势异常、可能缺水"——那才是 LLM 的位置。在那之前，LLM 是一个昂贵的 demo 道具。

## 主持人总结

### 共识点

1. **pump 是项目里唯一不套壳、唯一每天产出真实数据、唯一该被优先加固的部分。** 架构师被苏格拉底一问击穿，亲自翻 `stream.rs`（221 行）确认错误路径裸奔（`map_err(...)?` 往上抛、无持久化日志、无 retry、channel.send 用 `let _ =` 吞错误）。四票（架构师/编程手/恶魔/苏格拉底）一致优先 pump。
2. **本周数据动作收敛到唯一一个：`photos.batch_label TEXT`（可空）+ `list_photos(batch_label)` 命令。** plots 聚合根、实验设计五轴、agent_runs/steps 表全部推迟/放弃。建模手认输——"空集合上的投影不叫聚合根"。
3. **LLM agent 方向冻结。** 当前 LLM 没有不可替代的护城河（恶魔裁决 + 架构师最大让步）。所有"给 agent 加戏"的提案（ReAct 多轮、generate_report 工具、LLM 异常标注）暂缓。
4. **下一步顺序基本锁定，且不可调换：** pump 加固 → batch_label + list_photos → 纯模板导出 → 带可演示 Demo 去田野调研。恶魔明确反对跳过前四步直接做 generate_report。
5. **田野调研是对的方向，但必须先有可演示的稳定 Demo 做锚。** 恶魔修正了体验者——无 Demo 的访谈是空对空，育种员只会给你他们想象中的需求。

### 分歧点

1. **真值通道三件套（corrected_count/reviewed_by/reviewed_at）是否现在埋：** 建模手坚持必埋（承认 AI 会错是诚实，恶魔支持"唯一为被推翻做准备的设计"）；编程手认为无 review UI 前是空列、YAGNI。**折中：** 三列都是可空 ALTER、零迁移成本，先埋列不做 UI——但这是仍未拍板的点，需工程师定夺。
2. **导出要不要套 LLM：** 架构师说纯模板为主、LLM 异常标注作可关开关；恶魔说"无基准真值何来异常"、generate_report+LLM 是自欺。**倾向恶魔：** 第一阶段纯模板导出，不套 LLM。
3. **LLM 最终存废的哲学分歧：** 恶魔说当前 LLM 是"昂贵的 demo 道具、没有护城河"；架构师/编程手/建模手认为护城河在"跨实体关联推理"/"会调用工具的第二类用户"，但要等真实数据长出来才能兑现。**苏格拉底的终极问题一**把这个分歧留给了田野验证回答。
